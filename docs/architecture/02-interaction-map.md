## Scope, schema and confidence

This inventory records **738 original inspected elements/events: 641 design-affordance occurrences and 97 code-only controls/events**; implementation adds INT-739 (Retry save), for 788 current rows (INT-740–751 added in batch 2; INT-752–760 in batch 3; INT-761–772 in batch 4; INT-773–781 in batch 5; INT-782–788 in batch 6). Dynamic lists are inventoried by component/row template, not by unknown runtime patient counts. An element reference may identify the visible label inside a control; its containing field/button and nested glyphs were inspected together. Background shape, text, arrow and hit area are not counted as separate actions. Repeated screen/record occurrences retain individual node references and IDs.

`Confirmed` means code or explicit text establishes the stated behavior; `Inferred` means the design appearance/adjacent state suggests the intended behavior; `Unknown` would mean insufficient evidence even for the stated expectation. No exposed prototype connections were found. `Implemented` means source wiring exists, **not runtime success or screen completeness**. `Partial` means reduced/different behavior. `Missing` means no corresponding handler/control found. `Broken` denotes a demonstrable code contradiction such as a success label without persistence, wrong destination, or stale-state finalization; it does not claim a live reproduction. `Unverified` preserves ambiguous clickability or externally configured behavior. The exclusive screen-level statuses in 04 are a separate measure.

`UNKNOWN` destinations are deliberate. `SAME SCREEN` indicates a state change, not an invented route. Compound destinations describe conditional paths. External URLs are taken from code, not inferred from icon names. Per-screen preconditions apply to intended behavior; they do not assert that all current backend checks exist. Review [authorization findings](05-implementation-gap-analysis.md) before interpreting any clinical scope label as enforced.

Each table includes all requested fields. `FE-NNN` resolves to the source manifest below. Backend operation references resolve to the endpoint registry and UI→API chains in 04. For identical logical actions, the same destination/handler links occurrences while preserving separate interaction IDs.

## Deliberately noninteractive and ambiguous elements

- Device status bars, brand marks, static section headings, legends, source/provenance badges, payment/status chips, read-only clinical values and decorative arrows are not independently actionable unless they are part of an identified control.
- SCR-031 review checks at nodes 3131/3136/3141 and SCR-035 checks at 3620/3624/3628/3632 are review indicators; no prototype establishes independent toggles. They are excluded from action counts. Their missing review enforcement is still a gap.
- SCR-029 locked-record pills are unavailable context indicators in design, although the implementation uses `<button>` without handlers. They must not be treated as granting access.
- SCR-025 ON states and SCR-020 scope boxes imply selection; input mechanics are inferred. SCR-038 Review creation and SCR-039 Continue have a required duplicate-resolution gate in design; pictured blocker text is explicit even where color does not clearly communicate disabled state.
- SCR-045 arrival badge, SCR-049 per-record decision badges, SCR-052 biography/direct-preview buttons have ambiguous edit/click behavior. Their rows are retained as Unverified and do not imply live navigation.
- SCR-053 notification/practice/export/delete rows are `aria-disabled` divs, not functional settings. SCR-005 acceptance and auth social buttons are explicitly disabled. Staff stub navigation links are real links but all point to the stub.
- Header profile is a Clerk UserButton, not evidence of an implemented CliniX workspace switcher. Header alert glyph is aria-hidden and noninteractive. Designed alert/profile affordances remain distinct in the inventory.

## Conditional paths requiring verification

Check-in can interrupt at start or on response; normal result navigation must stay blocked after escalation. Booking review must preserve chosen doctor, visit mode, exact packet and expiry through submission. Appointment cancellation is exposed only for REQUESTED in current frontend, despite broader backend cancellation. Doctor dossier Begin Consultation does nothing when no REQUESTED/CONFIRMED appointment is returned. Prescription source loading can fail silently and remove the comparison pane; finalization still remains available. Local medication rows can be changed without saving before the confirmation appears. Draft deletion uses browser confirmation and is suppressed for APPROVED rows. Staff boundaries, membership expiry and role changes have no working implementation to verify.

Detailed trigger graphs, including unknown destinations and state actions, are in [06-master-navigation-graph.md](06-master-navigation-graph.md). The navigation projection is derived from these stable interaction records; it does not add prototype claims.
